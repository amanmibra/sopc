# The sopc format

This is the complete reference for writing sopc files, for people and for coding agents. If you are an agent asked to create or change voice-agent instructions in a sopc folder, read this whole file first, then follow the checklist at the end.

A full, commented example lives in [`examples/livekit-restaurant/sops/`](https://github.com/amanmibra/sopc/tree/main/examples/livekit-restaurant/sops). JSON Schemas for every file are in [`spec/`](https://github.com/amanmibra/sopc/tree/main/spec).

## The model in one paragraph

Each voice agent's prompt is assembled from blocks. There are two kinds. **Instructions** are shared prompt text that isn't a procedure (identity, brand voice, context, policy). **SOPs** are procedures (goal, steps, forbidden actions, warning signs). A block is self-contained: it says nothing about which agents use it. **Agents** are the one place blocks come together: one file per voice agent, with the platform it runs on, its own text (`context`), the blocks it uses in order (`blocks`), and values for placeholders. **Groups**, defined in `sopc.yaml`, name an ordered set of blocks that several agents share. Shared text is written once in a block and reaches every agent that lists it.

## Folder layout

```
<root>/                    any folder; a whole repo or e.g. sops/ inside one
  sopc.yaml                required; marks the root; defaults and groups
  instructions/<id>.md     shared prompt text, with optional YAML front matter
  procedures/<id>.md       SOPs in Markdown (recommended)
  procedures/<id>.yaml     or SOPs in YAML; both kinds can sit side by side
  agents/<id>.yaml         one per voice agent
  build/                   generated by `sopc`; never edit by hand
```

- **Ids are file names** without the extension: `instructions/brand-voice.md` has id `brand-voice`. Use lowercase kebab-case.
- Instructions, SOPs and groups share one set of names: an id must be unique across all three. An SOP is either `<id>.md` or `<id>.yaml`, not both.
- Files outside these folders are ignored.
- Every command works on `./sops` if `sops/sopc.yaml` exists, else on the current folder if `sopc.yaml` is there. Use `--dir` (or `-C`) for another folder; see [CLI.md](https://github.com/amanmibra/sopc/blob/main/CLI.md).
- A folder written for sopc v0.0.8 or earlier (with `bases/`, `inherits`, `exclude` or `agents:` targeting) fails with `old_format` errors. Run `sopc migrate` to convert it; see [CLI.md](https://github.com/amanmibra/sopc/blob/main/CLI.md#sopc-migrate).

## How a prompt is assembled

For each agent:

1. **The agent's `context`** comes first.
2. **Its `blocks`, in list order.** A group expands in place, in the group's order (groups may contain groups). Each instruction's text and each SOP is added as listed, so an instruction listed after the SOPs (e.g. a call closing) ends the prompt.
3. **The SOP heading** (`sops_heading`, `## Procedures` by default) goes once, right before the first SOP. Everything after it, SOPs and any instructions listed between or after them, follows in list order with no further heading. To leave the heading out, set `sops_heading: ""`.

Parts are separated by a blank line. Then every `{{name}}` placeholder is replaced: the agent's `variables` first, then `sopc.yaml` defaults. A placeholder with no value is a validation error.

Rules that keep the list unambiguous:

- Every id in `blocks` (and in a group) must be an instruction, an SOP or a group: anything else is `unknown_block`.
- A block may appear only once in an agent's expanded list, whether listed directly or through a group: twice is `duplicate_block`. List each block once, or take it out of the group.
- A group can't contain itself, directly or through other groups (`group_cycle`).

## sopc.yaml

```yaml
version: 1                          # always 1
variables:                          # defaults for {{placeholders}}, for every agent
  staff_transfer: the manager on duty
groups:                             # named, ordered sets of blocks
  delivery-orders:
    - allergen-check
    - delivery-handling
sops_heading: "## Procedures"       # heading before the first SOP (this is the default)
```

| Field | Type | Default | Meaning |
|---|---|---|---|
| `version` | `1` | `1` | Format version. |
| `variables` | map | `{}` | Default values for `{{placeholders}}`. An agent's own `variables` override them. |
| `groups` | map of name → list of ids | `{}` | Each group is an ordered list of instruction, SOP and group ids. An agent lists a group in `blocks` like a block, and it expands in place. |
| `sops_heading` | string | `"## Procedures"` | Placed once, before the first SOP in each prompt. `""` for none. |

Every field is optional. An empty `sopc.yaml` is valid.

## instructions/\<id\>.md

Markdown text, optionally preceded by YAML front matter between `---` lines. The text below the front matter is what goes into the prompt. The file says nothing about which agents use it.

```markdown
---
# Optional. Notes for people editing this file; they never reach a prompt.
---
Speak warmly and briefly. Ask one question at a time.
```

Instructions have no settings: the front matter, if any, holds comments (and `id`, which must match the file name). A file with no front matter is valid: it's plain text.

## procedures/\<id\>.md

An SOP is a procedure: a goal, when it applies, steps, things never to do, and warning signs. Like an instruction, it says nothing about which agents use it. Write it in Markdown (recommended) or in YAML (next section). Both read into the same SOP and compile to the same prompt.

```markdown
---
delivery: prompt
---
# Allergen check

**Goal:** Customer leaves knowing whether their order is safe for their allergy.
**When:** Any order where the customer mentions a food allergy or dietary restriction.

Parents often ask on behalf of a child. Confirm who the allergy is for first.

## Steps
1. Ask if anyone in the order has a food allergy
2. Check each item against {{menu_allergen_link}} `tool: lookup_allergens` `required`

## Never
- Never say an item is "allergen-free" or "safe"
- Never place the order before allergens are confirmed `tool: place_order`

## Warning signs
- Customer mentions anaphylaxis or an EpiPen; transfer to {{staff_transfer}} `tool: transfer_to_staff`
```

| Part | Required | Written as | YAML field |
|---|---|---|---|
| Settings | no | Front matter between `---` lines, settings only: `delivery` (and `id`, which must match the file name). YAML comments here never reach a prompt. | same names |
| Name | **yes** | Exactly one `# ` heading, the first thing after the front matter. | `name` |
| Goal | no, but warned about | `**Goal:** text` | `description` |
| When | no | `**When:** text` | `scope` |
| Guidance | no | Any other paragraphs between the name and the first `##` section. Line breaks are kept. | `guidance` |
| Steps | **yes, at least one** | `## Steps`, then a numbered list | `procedureSteps` |
| Never | no | `## Never`, then a `-` list | `forbiddenActions` |
| Warning signs | no | `## Warning signs`, then a `-` list | `warningSigns` |

<a id="sop-rules"></a>
The rules are strict, so every SOP reads the same and mistakes are caught:

- Names are exact and case-sensitive: `**Goal:**`, `**When:**`, `## Steps`, `## Never`, `## Warning signs`. Anything else (`**Objective:**`, `## Notes`, `### Details`) is an error that lists the allowed names.
- A field continues on the following lines until a blank line; the lines are joined with a space.
- Under a section, only list items (`- ` or `1. `). An indented line continues the item above it. Blank lines are fine.
- Sections may come in any order; `sopc fmt` puts them in the order above.
- A list item can end with markers in backticks, in either order: `` `tool: lookup_allergens` `` (the tool's exact name, one word) and `` `required` `` (steps only: the tool call must happen). An item with markers is the YAML object `{text, tool, required}`; without, a plain string.
- Notes for people go in front-matter comments (`# ...`). Everything in the body is prompt text.

## procedures/\<id\>.yaml

The same SOP in YAML. `sopc convert` switches SOPs between the two formats.

```yaml
name: Allergen check
delivery: prompt
description: Customer leaves knowing whether their order is safe for their allergy.
scope: Any order where the customer mentions a food allergy or dietary restriction.
guidance: |
  Parents often ask on behalf of a child. Confirm who the allergy is for first.
procedureSteps:
  - Ask if anyone in the order has a food allergy
  - text: Check each item against {{menu_allergen_link}}
    tool: lookup_allergens
    required: true
forbiddenActions:
  - Never say an item is "allergen-free" or "safe"
warningSigns:
  - text: Customer mentions anaphylaxis or an EpiPen; transfer to {{staff_transfer}}
    tool: transfer_to_staff
```

| Field | Type | Default | Meaning |
|---|---|---|---|
| `name` | string | required | Heading in the prompt. |
| `procedureSteps` | list of steps | required | Ordered steps; at least one. |
| `delivery` | `prompt` \| `auto` \| `tool` | `prompt` | See below. |
| `description` | string | `""` | **The goal**: the outcome that means the SOP succeeded. Write it. |
| `scope` | string | `""` | When the SOP applies. |
| `guidance` | string | `""` | Free text that isn't a step, forbidden action or warning sign. |
| `forbiddenActions` | list of steps | `[]` | Things the agent must never do. |
| `warningSigns` | list of steps | `[]` | Situations needing special handling, usually escalation. |

**Colons.** YAML treats `: ` (colon then space) inside unquoted text as a key and value. Quote any step or field that contains one:

```yaml
forbiddenActions:
  - "Never say: we're fully booked"    # quoted: fine
  - Never say: we're fully booked      # unquoted: error colon_in_step
```

For long text, a `|` block avoids quoting entirely.

**YAML version.** Files are read as YAML 1.2. Unquoted `yes`, `no`, `on`, `off`, times like `1:30` and dates are plain text. Only bare numbers (`- 10`) and `true`/`false` are read as something other than text, so quote a step that is just a number or a boolean. Duplicate keys in one mapping are an error. The boolean field `required` takes `true` or `false`; `yes`/`no` are accepted there too.

**Steps.** Each entry in `procedureSteps`, `forbiddenActions` and `warningSigns` is either a plain string or an object:

```yaml
- text: Check availability       # required
  tool: check_reservations       # optional: a tool the agent has
  required: true                 # optional, steps only: the tool call must happen
```

A step with a `tool` gets an instruction to use it ("Check availability. Use the `check_reservations` tool."), and the tool name is recorded in `build/lock.json`. Use the tool's exact name as the agent's code or platform defines it.

**Delivery.** Where the SOP's content goes:

| `delivery` | In the prompt | Fetched with the `get_sop` tool |
|---|---|---|
| `prompt` | everything | nothing |
| `auto` | name, scope, forbidden actions, warning signs | goal, guidance, steps |
| `tool` | name, scope | everything else |

Use `prompt` unless the agent is set up with a `get_sop` tool. Forbidden actions and warning signs stay in the prompt under `auto` because they must apply even if the agent never fetches the SOP.

## agents/\<id\>.yaml

```yaml
livekit: tonys-pizza                 # exactly one of livekit | vapi | elevenlabs | retell
context: |
  Tony's is a wood-fired pizza shop in Brooklyn. Pickup only after 10pm.
blocks:
  - restaurant-host
  - pizza-context
  - brand-voice
  - delivery-orders                  # a group
  - closing
variables:
  restaurant_name: Tony's Pizza
```

| Field | Type | Default | Meaning |
|---|---|---|---|
| `livekit` | string | — | LiveKit `agent_name`. |
| `vapi` | string | — | Vapi assistant id. |
| `elevenlabs` | string | — | ElevenLabs `agent_id`. |
| `retell` | string | — | Retell `agent_id`. |
| `context` | string | `""` | Text only this agent gets. It goes first in the prompt. |
| `blocks` | list of ids | `[]` | Instructions, SOPs and groups, in prompt order. |
| `variables` | map | `{}` | Values for `{{placeholders}}`. Override `sopc.yaml` defaults. |

Set exactly one platform field. Write `context` right after it, then `blocks`, so the file reads in prompt order. Elsewhere in sopc, refer to the agent by its id (the file name) or by its platform ref, e.g. `livekit:tonys-pizza` or `vapi:asst_9f3e`.

`blocks` and group lists are YAML lists. Write one id per line (`- brand-voice`), as above: it reads and diffs better. The inline form, `blocks: [restaurant-host, brand-voice]`, works too and compiles the same.

## Placeholders

`{{name}}` works in any text: instruction bodies, agent `context`, and every SOP field. Names use letters, digits, `_`, `-` and `.`. Each agent must have a value for every placeholder in the blocks it uses.

## Recipes

| You want | Do this |
|---|---|
| Text every agent gets | An instruction every agent lists, or a group every agent lists. |
| The same set of blocks in many agents | A group in `sopc.yaml`; each of those agents lists the group in `blocks`. |
| A family of agents with shared context | An instruction (e.g. `pizza-context`) that those agents list after the shared ones; or a group holding both. |
| Text one agent gets | That agent's `context`. |
| The same sentence with a different value per agent | A placeholder in the shared block, with each agent's value in `variables`. |
| One agent skips a shared SOP | Leave it out of that agent's `blocks` (or list that group's other blocks instead of the group). |
| One agent needs a different version of a block (e.g. a Spanish brand voice) | A second instruction; that agent lists it instead of the first. |
| Something said at the end of every call | An instruction each agent lists last. |
| A procedure only some agents follow | An SOP that only those agents list. |

## Converting an existing prompt

1. Split the prompt into: identity and voice (instructions), procedures (SOPs), and facts about this one agent (`context`).
2. Write each procedure as a Markdown SOP: the goal as `**Goal:**` and the trigger as `**When:**`. Turn numbered instructions into `## Steps`, "never"/"don't" lines into `## Never`, and "if the caller…, transfer/escalate" lines into `## Warning signs`. Put the rest in paragraphs under the name (guidance).
3. Text that appears in several prompts belongs in one instruction or SOP, not copied into each agent. List the blocks in each agent's `blocks` in the order the original prompt had them; use a group for a set many agents share.
4. Replace per-agent values inside shared text (names, links, phone numbers) with placeholders.
5. Run `sopc fmt`, then `sopc`, and compare the output to the original prompt. The agent's `context` comes first in the compiled prompt.

## Formatting and converting

`sopc fmt` keeps SOP files in one canonical style, and `sopc convert` switches SOPs between Markdown and YAML; neither changes a compiled prompt. See [CLI.md](https://github.com/amanmibra/sopc/blob/main/CLI.md#sopc-fmt) for how they work and what `--yes` allows.

## Validation

`sopc validate` reports these; every error names the file, as a path from the current folder, and Markdown errors give the line number (`sops/procedures/x.md: error [md_unknown_section] line 14: ...`). `sopc fmt` and `sopc convert` also report `convert_failed` (see above).

| Code | Severity | Meaning |
|---|---|---|
| `missing_config` | error | No `sopc.yaml` in the folder. |
| `invalid_yaml` | error | A file isn't valid YAML (including a key written twice), or isn't a mapping. |
| `colon_in_step` | error | A step contains `: ` and YAML read it as a key and value. Put the whole step in quotes. |
| `unquoted_value` | error | A step YAML read as a number or boolean (`- 10`, `- true`). Put it in quotes. |
| `empty_step` | error | A list item with nothing after the `-` (or only markers, in Markdown). |
| `invalid_field` | error | Unknown field, wrong type, missing `name`, or not exactly one platform. |
| `missing_steps` | error | An SOP has no steps: YAML `procedureSteps` missing or empty, or Markdown without `## Steps` or with no items under it. |
| `duplicate_file` | error | An SOP exists as both `<id>.md` and `<id>.yaml`. Keep one. |
| `md_settings_field` | error | A Markdown SOP's front matter sets something other than `id`, `delivery` (e.g. `name`); write it in the body. |
| `md_missing_name` | error | No `# <name>` heading. |
| `md_extra_name` | error | A second `# ` heading. |
| `md_text_before_name` | error | Text before the `# <name>` heading. |
| `md_heading_level` | error | A `###` (or deeper) heading. |
| `md_unknown_section` | error | A `##` heading other than `Steps`, `Never`, `Warning signs`. |
| `md_duplicate_section` | error | The same `##` section twice. |
| `md_unknown_field` | error | A bold label other than `**Goal:**` or `**When:**`, e.g. `**Objective:**`. |
| `md_duplicate_field` | error | `**Goal:**` or `**When:**` given twice. |
| `md_text_in_section` | error | Text under a `##` section that isn't a list item or an indented continuation. |
| `md_bad_annotation` | error | A malformed tool marker: `` `tool:` `` without a name, `` `tools: x` ``, `` `tool: two words` ``, or two tool markers. |
| `md_required_outside_steps` | error | `` `required` `` under `## Never` or `## Warning signs`. |
| `md_empty_section` | warning | `## Never` or `## Warning signs` with no items. |
| `id_mismatch` | error | An explicit `id:` differs from the file name. Usually just remove `id:`. |
| `duplicate_id` | error | An instruction and an SOP share an id, or a group has the name of one. |
| `duplicate_platform_ref` | error | Two agents point at the same platform agent. |
| `unknown_block` | error | An agent's `blocks` or a group lists an id that isn't an instruction, SOP or group. |
| `duplicate_block` | error | A block appears twice in an agent's expanded list (listed twice, or both directly and through a group). |
| `duplicate_rule` | error | Two steps, two nevers or two warning signs of one SOP have the same text (ignoring whitespace), so they would share a rule id. |
| `group_cycle` | error | Groups contain each other in a loop. |
| `unset_variable` | error | A placeholder has no value for some agent. |
| `old_format` | error | A field or folder from the format of sopc v0.0.8 and earlier: `bases/`, `inherits`, `exclude`, `position`, `agents` on a block, `instructions` on an agent, `sop_order`. Run `sopc migrate`. |
| `removed_field` | error | `locked`, which sopc v0.0.9 and earlier read, on an instruction or SOP. It no longer exists; run `sopc migrate` to remove it, or delete the line. |
| `migrate_failed` | error | `sopc migrate` can't convert a file exactly (or the folder is partly migrated); nothing is written. |
| `missing_goal` | warning | An SOP has no goal (`**Goal:**` or `description`). |
| `unused_block` | warning | No agent uses an instruction or SOP, directly or through a group. |

## Checklist for coding agents

1. Find the sopc root: the folder containing `sopc.yaml`.
2. Before adding text to an agent, check whether an instruction or SOP already covers it. Prefer editing the shared block over copying text into agents. To give an agent a block, add its id to the agent's `blocks` where it belongs in the prompt (or to a group the agent uses).
3. Change only files in `instructions/`, `procedures/`, `agents/` and `sopc.yaml`. Never edit `build/`.
4. Run `sopc validate` and fix every error. Commands use `sops/` (or the current folder) by default; if the root is elsewhere, pass it to each one, e.g. `sopc validate path/to/root`.
5. Run `sopc plan` (it compares with the default branch; `--against REF` to choose) and confirm that only the agents you meant to change appear.
6. Run `sopc lint`. If your change introduced a duplicate or conflict, fix it; report pre-existing ones to the user.
7. Run `sopc fmt`, then `sopc` so `build/` matches.
8. Never pass `--yes` to `sopc fmt` or `sopc convert` on your own. If one of them lists a file it won't rewrite because comments would be lost, tell the user and let them decide. The same goes for `sopc migrate`: show the user its plan, and run it with `--yes` only once they approve.

To convert existing prompts into this format, follow the `sopc-import` skill (`sopc skills install`).
